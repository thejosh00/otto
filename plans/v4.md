# Plan: otto v4, keeping up with what gets built

**Status:** Draft. Nothing here starts until v3 is done, and the person reviews this plan again then.
**Written:** 2026-11-07, against `1e8966a`. Line references, numbers and v3's phases will have moved by
then, so check them first ([Before starting](#before-starting)). Sizes are estimates, not measured.

Commands and fields marked *(proposed)* don't exist yet. Like `v3.md`, this file lives outside `docs/`
because `src/doc_examples.rs` runs every `otto` command there.

## The problem

Building is no longer the bottleneck. Knowing what got built is.

From each run's `changes/index.json`, 2026-10-22 to 2026-11-07, 50 changes:

| Size of change | Approvals | Median time from submitted to approved |
|---|---|---|
| Under 100 lines | 15 | 2.8 min |
| 100 to 499 lines | 20 | 2.5 min |
| 500 lines or more | 12 | 2.4 min |

- Time spent doesn't grow with size. The +1120 change 12/20 was approved in 37 seconds.
- 2 of the 50 were sent back.
- Summaries raise decisions ("Decide: whether you're happy with UTC"). Approving quickly lets the author's
  choice stand without anyone really deciding it.

This time is an upper limit on review, since the person may not have been looking when a change arrived.
These numbers don't prove a change was reviewed badly. They do show that review can't be doing the job
`v3.md` gives it: "A harmful patch you approve. That's what review is for."

The Vision already says the person verifies from evidence and doesn't read every line, so asking them to
read harder is the wrong fix. v4 is about what they look at instead.

## Three questions, and what answers each

| Question | Today | v4 |
|---|---|---|
| **What's going on, and what needs me?** | `otto ls`, the inbox, one page per run | [The brief](#phase-1-the-brief) |
| **What did this change do, and does it work?** | The author's summary and evidence | [Review that fits the time available](#phase-2-review-that-fits-the-time-available), the witness, [sequence diagrams](#phase-5-checked-sequence-diagrams) |
| **What does the app do now?** | READMEs, `DESIGN.md`, `docs/`, memory | [Living descriptions](#phase-3-living-descriptions), [checkups](#phase-4-checking-what-the-person-knows) |

The third question matters most. Understanding each change well still doesn't add up to knowing the system
after 50 of them.

## The work at a glance

| Phase | What | Why | Size | Needs from v3 |
|---|---|---|---|---|
| 0 | Baseline | So v4 can be judged by numbers | S | Nothing |
| 1 | The brief | One place that says what matters, across all runs | S, then M | Phase 1, for its profile |
| 2 | Review that fits the time available | Spend attention where only a person can add something | M | Phase 2 and Phase 4, helpful |
| 3 | Living descriptions | Review behaviour, not diffs; know the app as it is | L | Phase 3, for instructions |
| 4 | Checking what the person knows | A real measure of understanding | S | Nothing |
| 5 | Checked sequence diagrams | A picture of order, for changes where order matters | M | Nothing |

The order runs from cheapest to dearest, except Phase 5, which waits because it helps fewer changes. Phases 1
and 4 start as trials that need almost no otto code.

## Rules for every phase

1. **Recorded or checkable.** Anything that explains the system comes from what otto recorded or is checked
   against the code, and links to its source. A wrong diagram in the PR Lens trial looked as convincing as a
   right one.
2. **It replaces reading.** The Vision rules out "more process for me: new gates, more questions, longer
   reports". Each item says what the person no longer has to read. If it can't, it doesn't get built.
3. **No new gates per change.** Approving stays one action.
4. **Try it before building it.** Each phase with a trial has a bar, and missing the bar ends the phase. The
   bars are judgement, and the person can move them.
5. **Explaining agents can't act.** They run read-only under a sandbox profile, because they read what every
   other run wrote, including runs that read the web.
6. **v3's rules still hold.** Runs survive every release, rollback stays real, each item is one change, and
   additions to run data are additive.

## Phase 0: baseline

- **0.1 Review measures (S).** Turn the numbers above into something repeatable: `otto changes --stats`
  *(proposed)* or a script in `scripts/`. It reports time to approve by size, send-backs, and how many changes
  raised a decision.
- **0.2 First checkup (no otto code).** Set up otto as a lectio subject and take one checkup, as in
  [Phase 4](#phase-4-checking-what-the-person-knows). This gives a starting score.

**Measures.** The first three come from otto's records. None has a target yet, because a faster approval
isn't better or worse by itself.

| Measure | Now | Hoping to see |
|---|---|---|
| Decisions raised and answered by the person | Not recorded | Most |
| Changes sent back because they were wrong | 2 of 50 | More at first, as problems get seen |
| Time on "read this" changes compared with the rest | No difference by size | Clearly more |
| Checkup score on each app | None yet | Rising |
| Problems found after landing that review could have caught | Not recorded | Falling |

## Phase 1: the brief

A short page across all runs, in three parts:

```text
Needs you (2)
  11/12 the witness: decide whether to start its trial
  otto-driver: D1, Seatbelt or a separate user

Changed since you last looked
  otto: a kill now records who held the lock and whether it landed
  cloudgpu: capacity is now logged; first real sample looks right

Looks off
  architect-build has failed on the same step twice
  3 changes landed with parts marked unverified
```

Status and "needs you" come from code, which already knows them and can't misreport them. "Changed" and
"looks off" need reading across runs, so an agent writes them. Nothing shows "builder ran tests", and a quiet
day is one line. Each line links to its source. Each agent's own one-liner stays beside it on the front page,
since those already exist.

It updates when something changes, not constantly. A feed that moves all the time becomes one more thing to
skim.

- **1.1 Trial (no otto code).** A read-only run with new instructions (`workflows/brief.md`) reads `otto ls`,
  the inbox, changes and recent handoffs, then publishes one page with `otto state publish`. A check script
  keeps it asleep when nothing has changed. Run it for two weeks.
- **The bar.** The person opened it most days, and it changed something they did or caught something they'd
  have missed at least twice. It was worth what `otto usage` says it cost. Otherwise, stop here.
- **1.2 On the front page (M).** Show it at the top of the agents page (`#/`), with a mark for "since you last
  looked" that the web page and `otto brief` *(proposed)* share. The inbox line stays where it is.
- **1.3 Pick one to read (S).** Each week it names the one change most worth a proper look: largest risk,
  least evidence, or a claim that changed.

**What the person stops reading:** the list of every run and every change, to find what matters.

## Phase 2: review that fits the time available

- **2.1 Decisions as data (M).** `otto state change submit --decide "<question>"` *(proposed)*, repeatable.
  The page and `otto changes show` put these first, each with a place to answer, sent to the author as with
  `otto changes answer`. Approving without answering stays allowed and is recorded as "left to the author",
  so a choice nobody made is visible and doesn't look like one the person did.
- **2.2 Which changes to read, by rule (M).** The Vision's "Where I still read" list is prose, and authors
  apply it unevenly: 1 of those 50 summaries says so. Make it a per-repo list of paths *(proposed)*, such as
  `src/changes.rs`, `workflows/land-flow.md`, `skills/**` and anything under auth. A change touching one is
  marked **read this** in the list and on its page, whatever its author said.
- **2.3 Explain this change (S).** A button on the page that opens `otto chat` with the author's run, asking
  what behaviour changed and what would break if it were wrong. It uses what exists and makes it one click.
- **2.4 The witness on the page (needs its trial to pass).** M2 to M4 of
  `~/workspace/ideas/plans/change-witness.md`, already planned there. It stays outside the approval path.

**What the person stops reading:** whole summaries of routine changes, down to the decisions and what could
go wrong.

Items 2.1 and 2.2 touch the approval path, so they're "read this" changes themselves.

## Phase 3: living descriptions

A short document per app saying how it behaves, in claims that can be checked. It's the core of v4.

```markdown
## Killing a wake

- [kill.finished] Poke never kills a wake whose recorded wake has finished: it skips and looks again.
  (`poke::decide`; test `a_finished_wake_past_its_deadline_is_not_killed`)
- [kill.evidence] A kill records who held the lock and whether a signal or tmux kill landed.
  (`poke::kill_wake`; test `a_kill_says_what_it_acted_on_and_that_a_signal_landed`)
```

Each claim has a stable id, plain words, and a citation of a symbol and a test. It cites symbols, not line
numbers, which go stale. It lives in the repo as `BEHAVIOUR.md` *(proposed)*, so it changes in the same commit
as the code and lands with it. It isn't a replacement for `docs/`: those say how to use the app, and this says
what's true of it, in a few pages. A claim that can't be kept short doesn't belong.

- **3.1 Trial on one app (S).** Write it by hand for otto, and have the person read it. **The bar:** it taught
  them something they didn't know or had wrong, and it stayed under about 5 pages. Otherwise, stop here.
- **3.2 Check it (M).** `otto describe check` *(proposed)* confirms that cited symbols and tests exist at a
  commit, and that ids are unique.
- **3.3 Changes say what they alter (M).** A change names the claims it adds, alters or removes. The page
  opens with those in plain words, such as "kills now skip a wake that has finished", and links to the
  evidence for each. If a change touches cited code and declares nothing, the page says so. That's a warning,
  because most edits don't alter behaviour.
- **3.4 Drift check (M).** A read-only run samples claims each week, reads the code and tests, and tries to
  show each claim false. What it finds goes in the brief under "looks off". The author's claim is never its own
  proof.
- **3.5 More apps.** Add them where it pays: lectio next (44 commits in 30 days, 213 source files), then
  cloudgpu. Legenda and omnifactum changed little in that time (5 and 7 commits), so they can wait.

The brief's "changed" part can read claim changes once they exist, and its summaries stop being guesses.

**What the person stops reading:** diffs, for most changes, in favour of what changed in behaviour.

## Phase 4: checking what the person knows

Otherwise nothing tells the person whether they understand their own apps, including how much of it they only
feel they understand.

- **4.1 Trial (no otto code).** Add otto as a lectio subject with `lectio subject add`, and let
  `lectio-teach` and `lectio-examine` do what they already do. The examiner writes checkups without seeing the
  lessons, so it's a fair measure. **The bar:** after a month, the score moved, and the person found it worth
  doing rather than one more chore.
- **4.2 Teach from the description (S).** Once Phase 3 exists, the syllabus comes from `BEHAVIOUR.md`, and a
  changed claim brings its concept back for review. Otto and lectio stay separate, joined only by a run using
  each one's CLI.
- **4.3 Weak spots steer attention (S).** A concept the person keeps missing marks changes that touch it as
  worth reading in the brief.

## Phase 5: checked sequence diagrams

As in [`ideas.md`](ideas.md#checked-sequence-diagrams-on-changes): a small file of ordered steps, checked
against the code, and drawn by otto's page. It helps when a change is about order, and little otherwise.

- **5.1 Replay (S), and the gate.** Write the files for 12/11, 12/16 and 12/20, including the two original
  mistakes, and confirm the checks flag both. If they don't, stop here.
- **5.2 Build it (M).** The file format, the checks and the drawing, used on the next 10 or so changes where
  order matters.
- **5.3 The same drawing for wakes (S).** `otto why`'s timeline drawn as a sequence, from what otto recorded.

## Set aside

- **Landing without the person's approval.** Most changes already get little review, so this would give up less
  than it sounds. But it needs an independent check that has proven itself, and the witness hasn't yet. See
  [V1](#decisions-for-you).
- **A live activity feed.** See Phase 1.
- **A hold on new work when the person falls behind.** A useful backstop, and a new kind of gate, so it stays
  out unless the measures say it's needed.
- **PR Lens itself.** Changes land with no pull request, otto's evidence refuses SVG, and its instructions are
  about 74 KB. Its idea of showing order is what's kept.
- **Architecture overviews, animation and a canvas.** The overviews were tangled on two of three changes.

## Decisions for you

| # | Decision | My recommendation |
|---|---|---|
| V1 | Should routine changes ever land without approval? | Not in v4. Decide after the witness has run on every change for a while, with its record to judge by |
| V2 | Where do descriptions live? | In each repo, so they land with the code |
| V3 | Which app comes first? | Otto. It changes most and it's where a mistake costs most |
| V4 | Does the witness continue? | Already its own decision: the `shadow-verdict` gate at the end of its trial |
| V5 | Should the Vision change? | It's your document. Its test, approving "from the summary and evidence alone", passes even when nothing is really checked, and it has no goal for knowing the app. You may want to add both |

## How this gets built

The v3 loop: `otto-driver` hands off one item, `otto-build` builds it, the person approves, and the driver
checks it from cold. Two things have to change for v4:

- **A new driver run.** The driver's goal names `plans/v3.md`, and a goal's text can't be edited.
- **`workflows/drive-flow.md` names `plans/v3.md` too.** Make the plan's path something the run supplies.

As each piece lands, use it to review the next. If the brief or the decision list doesn't help with v4's own
changes, that's the first evidence against it.

## Before starting

1. Re-read this plan against what v3 became. Phase 4 of v3 moves `changes.rs` and the web code, and Phase 3
   changes where instructions live, so items here may belong in a different place.
2. Rerun the baseline. The numbers above predate any change in how reviews are done.
3. Check what has already happened: the witness's verdict, and any lectio checkups.
4. Answer V1 to V3 and V5, or change them.
5. Check whether the theme is still the right one. If keeping up has stopped being the problem, this plan
   shouldn't run just because it's written.

These can start before v4 with no plan, and feed it if they do: the witness trial, the otto lectio subject, and
the brief's trial run.

## Risks

| Risk | Effect | Response |
|---|---|---|
| Explanations make the person feel informed without being so | Worse than today: less looking, same confidence | Rule 1, and Phase 4 measures it |
| It adds reading instead of replacing it | The Vision's "not wanted", and it gets ignored | Rule 2, and the trial bars |
| The description rots or says false things | It's trusted and wrong | Checks in 3.2, warnings in 3.3, drift check in 3.4 |
| Authors declare claims carelessly | Behaviour changes with no sign of it | The warning catches some. The drift check catches some later. Neither catches all |
| A hostile page steers the agent writing the brief | A misleading brief | Rule 5 limits it to words; links let the person check |
| Token cost | About 260M tokens a week across runs already (`otto usage`, 133 wakes) | Trials measure it; check scripts keep quiet runs asleep |
| The checkups feel like homework | Dropped, and the measure goes with them | Phase 4's bar asks this directly |

## Done means

- **Phase 0:** the baseline can be rerun with one command, and a first checkup score exists.
- **Phase 1:** the brief is on the front page, or its trial missed the bar and the reason is recorded.
- **Phase 2:** decisions are answered or visibly left to the author, and "read this" comes from a rule.
- **Phase 3:** otto has a description that passes its check, changes say which claims they alter, and the drift
  check has run for a month. Or its trial missed the bar, and the reason is recorded.
- **Phase 4:** checkup scores exist over time for at least otto.
- **Phase 5:** the replay caught both mistakes and the feature is in use, or it failed and was dropped.
- **Throughout:** the person can answer questions about their apps from memory better than at the baseline, and
  says v4 takes less of their time than it gives back.
