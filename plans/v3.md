# Plan: otto's next version

**Status:** proposed, nothing built. **Written:** 2026-11-06, against `7fc652b`. Line references are
to that commit.

`DESIGN.md` already calls the current system v2, so this is v3 by its count. Like v2, it is mostly a
matter of taking things out of the middle: a smaller kernel, safety rules the operating system
enforces instead of prose asking for them, and the existing runs carried across without losing
anything.

It is not a rewrite. The engine works: of 246 wakes on this machine, 11 ended incomplete, and one of
those was the false kill in Phase 0.

This file lives outside `docs/` on purpose. `src/doc_examples.rs` runs every `otto` command in
`docs/`, and commands marked *(proposed)* here don't exist yet.

## The work at a glance

| Phase | What | Why | Size | Migrates run data? |
|---|---|---|---|---|
| 0 | Poke kill fix | A healthy wake can be killed as it starts | S | No |
| 0b | Debuggability | The Sep 28 kill couldn't be fully explained from what otto recorded | S–M | Additive |
| 1 | Enforced safety (change 1) | Every run has full access, and "only the lander pushes" is prose | L | **Yes: every active run, by wave** |
| 2 | Typed events (change 3) | Notes became an event bus parsed by string prefix | M | Additive |
| 3 | Modular harness (change 4) | One 43KB procedure for every wake | M | Per-run setting |
| 4 | Kernel and apps (change 2) | Landing has outgrown the runtime around it | L | No: layout on disk is unchanged |
| 5 | Execution seam (change 5) | Hard dependencies on macOS and on `claude` internals | S–M | No |
| M | [Migrating existing runs](#migrating-existing-runs) | Runs through all of the above | | |

**The build order differs from the order I first gave.** The kernel split moves from second to
fourth, because typed events and harness modules each pull an app's parts away from the core. Doing
them first makes the split mostly a move of code that's already separated. Doing it first would mean
designing app interfaces around prefixes and a monolithic harness that are about to go away.
Debuggability goes before all of them, because every later phase relies on being able to tell what
happened.

**Not in this plan:** run-to-run handoffs and learning from your reactions. Both were suggested
alongside these changes and both get easier after Phase 2, but neither is scheduled here.

## Rules for every phase

1. **Runs survive every release.** The invariants in [Migrating existing runs](#what-must-survive)
   are checked before each cut-over.
2. **Rollback stays real.** See [Rollback](#rollback) for two ways it can break today.
3. **Each item is one change**, reviewed and landed alone, leaving `main` working.
4. **A fix has a test that fails without it.** Anything a model reads also needs `test/live.sh`, as
   the README already requires.
5. **Docs move with the code**, including `docs/reference/run-json.md`, `journal.md` and the
   generated CLI reference.
6. **Turning enforcement on is your act.** A run can build the sandbox, but no wake moves a run into
   or out of it.
7. **Every decision otto makes about a run says why.** A new kill, skip, refusal or denial records
   the evidence it acted on, so a later reader doesn't have to reconstruct it.

## Phase 0: the poke kill fix

**The bug.** `decide()` (`src/poke.rs:121`) kills when the wake lock is held and the last recorded
deadline has passed. It never checks whether that recorded wake already finished. On Sep 28 this
"killed" wake 44, 20 hours after it completed normally, with poke running every 5 minutes throughout.
What held the lock isn't recorded. The likeliest cause is another process's lock probe, which took
the lock exclusively until `d864ce9`. A test on current `main` confirms the decision still returns
`Kill`.

**What's still exposed:**

- A wake takes the lock at `src/wake/mod.rs:207` and records its new deadline shortly after. A poke
  pass in that gap kills the new wake's tmux session. The lander is the most exposed, since approving
  a change starts it immediately. The race itself hasn't been triggered, only the decision.
- `kill -TERM -<pid>` (`src/spawner.rs:162`) signals the recorded pid, which may be long gone and
  could by now be a different process group. `otto stop` (`src/core.rs:1698`, `:1768`) uses the same
  function.

**Items:**

- **0.1 Only kill an unfinished wake (S).** In `decide()`, kill only when `wake.outcome.is_none()`.
  If the lock is held and the recorded wake finished, skip with the reason "a wake is starting" and
  look again next pass. Tests: finished wake plus held lock skips; unfinished wake past its deadline
  still kills.
- **0.2 Don't signal a finished wake's pid (S).** In `spawner::kill`, signal the pid only when the
  recorded wake has no outcome. Test it through both `otto stop` paths.

**Accepted cost:** an `otto wake` that hangs inside that short gap is never killed by poke. Today's
behaviour can kill healthy work, so this is the better risk.

**Migration:** none. The false `wake-incomplete` stays in the journal, which is append-only.

## Phase 0b: debuggability

**The problem.** Investigating the Sep 28 kill took three rounds of reading logs and code, and still
ended in "most likely". What otto couldn't say:

| Question | Why it couldn't be answered |
|---|---|
| Who held the lock? | Nothing records a lock's holder |
| Did the kill hit anything? | `kill_wake` discards `spawner::kill`'s result (`src/poke.rs:409`) |
| Why did this wake start? | `wake-started` has no cause (`src/event.rs`), so it's missing for all 246 wakes |
| What was the web UI doing then? | `serve.log` lines have no timestamps |
| Why didn't this run wake? | A "nothing new" check result is deliberately not journaled; only the latest is kept in `run.json` |

The information is also spread across the journal, `poke.log`, `serve.log`, `run.json` and transcripts,
with nothing joining them. `poke.log` is 15,693 lines and growing, mostly "nothing due", with no rotation.

**Items:**

- **0b.1 Why a wake started (S).** Add `cause` to `wake-started`: period, check changed, check safety net,
  gate answered, note, person, change landed or approved, retry. Absent on old lines, which read as
  "not recorded".
- **0b.2 Evidence on a kill (S).** A wake writes its pid, its number and the time beside the lock when it
  takes it. `wake-killed` then records the holder if known, the deadline and outcome it acted on, and
  whether a signal or tmux kill landed. This is what would have settled Sep 28.
- **0b.3 Check history (S).** Keep a capped per-run file of recent check results, with time, exit code and
  note. It stays out of the journal, as `DESIGN.md` §8.1 intends, but "why didn't it wake?" has an answer.
- **0b.4 Logs you can read (S).** Timestamps on every `serve.log` line. Rotate `poke.log`. Poke notes when
  the gap since its last pass is far longer than 5 minutes, which also serves D4.
- **0b.5 One timeline (M).** `otto why <run> [--wake <n>]` *(proposed)* merges the journal, poke's decisions
  about that run, check history and later sandbox denials into one ordered account, with the transcript's
  path for each wake. It reads existing files and writes nothing. The test: given a copy of today's
  `~/.otto`, it shows the Sep 28 sequence in one screen, with what wasn't recorded back then marked as such.

**Later phases add to this:** Phase 1's denial report (1.7) feeds the timeline, Phase 2's `from` and `about`
fields show where a note came from, and Phase 3 records which harness modules a wake was given and which it
loaded on demand.

**Deliberately not included:** tracing frameworks, metrics services or dashboards. otto's state is already
files on one machine, so reading them well is enough.

**Migration:** none needed. New fields are additive, and old records display as "not recorded".

## Phase 1: enforced safety

**The problem.** All 16 runs use `bypassPermissions`, neither configured launcher sandboxes anything,
and every wake's working directory is the whole of `~/workspace`. Nothing but harness prose stops a
wake from pushing with your `gh` credentials, and some runs read the web, so a hostile page can steer
one.

**The goal, as a test.** A wake steered by hostile content cannot push, cannot approve its own
change, cannot reach another project's files unless granted them, and cannot leave the sandbox.

### Spike first (1.1)

These decide the design and I haven't verified them. `sandbox-exec` runs on this machine; `nono` isn't
installed.

1. **Keychain.** `gh` keeps its token in the keyring and git uses it through a credential helper.
   Claude's own sign-in probably lives in the Keychain too. Can a sandbox allow one and refuse the
   other? **This is the question most likely to change the plan.**
2. **Report mode.** Can a Seatbelt profile log denials without enforcing them? [Observation](#the-waves)
   depends on this.
3. **Other things a wake needs:** subagents, MCP servers, `bun`, `cargo`, `uv`, `tmux` in live tests.
4. **Private repos.** `otto` and `lectio` are public, so fetching needs no credentials. Check the
   other repos `architect-build` can touch.
5. **Ship scripts.** Does any repo in play land through its own script, which 1.5 would have to
   replace?

**Options for separating credentials, in order of preference:**

| Option | For | Against |
|---|---|---|
| Seatbelt profile, plus clearing credential variables and helpers | Built in; fits the existing launcher mechanism | Keychain may not split; Apple has deprecated `sandbox-exec`, though it still works |
| A separate macOS user for wakes | Strongest credential separation | Needs its own Claude sign-in; file sharing, tmux and transcripts all get harder |
| Clearing variables and helpers alone | Trivial | Not enforced. Useful as a layer, not as the control |

**Decision rule:** use Seatbelt if the spike shows `gh` and git credentials can be refused while
`claude` still signs in. Otherwise use the separate user.

### Escapes the sandbox must close

Filesystem rules alone aren't enough. Each of these gets past a naive profile, and each gets a test:

| Escape | Why it works today | Fix | Item |
|---|---|---|---|
| Check scripts | Poke runs them unsandboxed (`src/poke.rs:313`), and a wake can write them | Run them under the run's own profile | 1.3 |
| Self-approval | Review state is in `runs/<id>/changes/index.json`, which the authoring wake can write | Keep approvals somewhere wakes can't write | 1.4 |
| Lander runs author code with credentials | Land-flow runs the change's tests, then pushes, in one credentialed process | Take credentials away from the model | 1.5 |
| Git hooks and config | Worktrees share `<repo>/.git`, so a planted hook runs in the lander | Deny writes to `.git/hooks` and `.git/config`; push with hooks disabled | 1.2, 1.5 |
| Claude settings | `~/.claude` must be readable and transcripts writable, but hooks in `settings.json` run code | Deny writes to settings, hooks and skills; allow `projects/` | 1.2 |
| Other otto state | `$OTTO_HOME` is granted whole, including `config.json` and other runs | Write access to its own run, repo locks and `feedback.jsonl` only | 1.2 |
| Talking to outside processes | The tmux server, `launchctl`, `open` and `osascript` all run things outside the sandbox | Deny the tmux socket and those services | 1.2 |
| Persistence | Shell startup files, `~/Library/LaunchAgents`, `~/.local/bin` | Deny writes | 1.2 |
| `otto-build` installing | Its goal says to run `./install.sh`, which replaces the binary poke runs | [Decision D2](#decisions-for-you) | D2 |

### Items

- **1.1 Spike (M):** the questions above. Its output is a written answer and one working profile.
- **1.2 Profiles, on the existing launcher mechanism (M).** A launcher is already a command in front
  of `claude`, and a run records only its name (`docs/guides/sandboxing.md`). So a sandbox is a
  launcher whose command is `sandbox-exec -f <profile> … claude`, with profiles under
  `$OTTO_HOME/sandbox/`, outside any grant. Three benefits: `run.json` needs no new field, an older
  binary still understands it, and rollback keeps working. `otto wake` stays outside the sandbox as
  the validator and deadline keeper; only its child is confined.
- **1.3 Sandboxed check scripts (M).** Poke runs a run's check under that run's profile. Check scripts
  stay where they are, since a wake tampering with its own check now hurts only itself. Include a
  test that a check can't write outside its run.
- **1.4 Approvals outside the wake's reach (M).** Approving writes a record to `$OTTO_HOME/approvals/`
  with the commit and patch-id. `otto state change check` trusts only that record. `index.json` still
  says what state a change is in, but it's no longer the authority.
- **1.5 No model holds push credentials (M).** The lander's wake runs tests and rebases in the
  sandbox, then records a request to land. Its `otto wake` parent, outside the sandbox and running no
  model, checks the approval and patch-id and pushes with hooks disabled, then records the result.
  Poke is the backstop if that parent dies. Update `workflows/land-flow.md` and its live tests.
  **Limit:** this covers `direct` repositories, which is all of them today. Pull-request mode needs
  `gh`, so it keeps a credentialed lander until the same approach is built for it.
- **1.6 Sandboxed by default (S).** A new `otto run` gets a sandbox. Going without one needs an
  explicit flag, and the run's page says so. Do this last, once the waves below have proved the
  profiles. Rewrite `docs/guides/sandboxing.md`, and update the README's "Give push to the lander
  alone", which becomes something otto does rather than advice.
- **1.7 Observe and enforce commands (S).** `otto sandbox observe|enforce|off <run>` *(proposed)*,
  plus a report of what each observed run was denied. Person-only: refused when `OTTO_RUN_ID` is set,
  and blocked by the profile anyway.

### Acceptance test

`tests/live_sandbox.rs`, run by a real model with a goal that tells it to try: push; read `~/.ssh`;
write to another project; edit `.git/hooks`, `~/.claude/settings.json` and `config.json`; approve its
own change; start something through tmux and `launchctl`. All must fail. The same run must still be
able to commit, submit a change, and have it land.

### What this does not close

- **Sending out what a wake can read.** Web-reading runs need the network, and Seatbelt can't allow
  by hostname without a proxy. Removing credentials and secrets from reach limits the damage.
- **A steered wake damaging its own run**, including its own `run.json`, or answering its own gate.
  Answers can't authorize a push any more, since no model can push.
- **A harmful patch you approve.** That's what review is for.

## Phase 2: typed events

**The problem.** A note was meant to be a person talking to a run. Now 12 of the 13 most recent notes
I could read came from the change system. Code and prose both depend on the text:

- Written: `src/changes.rs:63`, `src/outputs.rs:578`, `src/messages.rs:363`
- Parsed: `src/story.rs:432`
- Taught: `harness/wake.md:351`, `:381`, `:428`; `workflows/dev-flow.md:288`
- Outside this repo: `~/.claude/skills/architect-build/SKILL.md:81` and `:88`

There's also a safety problem. A reviewer's comment reaches a wake inside a note, and a note is
presented as a person's words. Third-party text should be labelled as third-party text.

**Design.** Keep the notes machinery, because at-least-once delivery tied to wake completion is good
and already tested. Add what a note is about and who it came from:

```jsonc
// a note in run.json; both fields optional, absent means a person's own note
{ "id": "014", "file": "notes/014.md",
  "from": "otto",                                     // person | otto | reviewer | ci
  "about": { "kind": "change", "ref": "10", "version": 1, "event": "landed" } }
```

The prompt then has two parts: **Notes from the person**, and **What happened to your work**, with
third-party text marked as data to weigh, not instructions.

**Items:**

- **2.1 Keep fields an older binary doesn't know (S).** Add a catch-all flattened field to `RunState`,
  so unknown keys survive a rewrite. It ships first, because it's what makes later rollbacks safe.
- **2.2 Write the fields (S).** Changes, outputs and messages set `from` and `about`. The text keeps
  its prefix, so nothing that reads it breaks yet.
- **2.3 Use the fields (M).** `story.rs` reads `about` first and falls back to the prefix. The fallback
  stays permanently, because old notes never change.
- **2.4 Split the prompt (M).** `with_notes` renders the two parts. Needs a new live test, including
  a reviewer comment that tries to give an instruction, and reruns of `live_note`, `live_changes` and
  `live_changes_pr`.
- **2.5 Move the readers (S).** Update the harness and `dev-flow.md`, then `architect-build`'s skill.
- **2.6 Stop adding prefixes to new notes (S),** after one full cycle with no regressions.

**Migration:** none needed at cut-over, but check [notes in flight](#what-must-survive). Existing notes
without the fields are a person's by default, which is correct for `gtd-task-runner`'s standing note 001.

## Phase 3: modular harness

**The problem.** Every wake gets all 43KB of `harness/wake.md` through `--append-system-prompt`
(`src/wake/launcher.rs:71`). `lectio-teach` is told how to land code. And any edit means re-testing
behaviour nobody changed. The main gain is correctness and narrower testing. It won't save many
tokens: wakes that made no progress were only 8% of all tokens.

**Design.** A core plus modules, with no silent gaps:

| Module | Size today | Live tests |
|---|---|---|
| Core: orient, stop, handoff, gates, notes, translation, undoable actions, staying cheap | ~23KB | `live_gate`, `live_note`, `live_background`, `live_feedback` |
| `changes` (with repo locks) | 5.2KB | `live_changes`, `live_land_tests`, `live_change_summary` |
| `check-scripts` | ~4.5KB | `live_wait` |
| `checking-done` | 3.0KB | `live_verify` |
| `outputs` | 2.6KB | `live_outputs` |
| `messages` | 1.9KB | `live_message` |
| `todo` | ~1.5KB | `live_todo` |
| `skill-files` | 1.3KB | |

**Selection can't rely on guessing.** `gtd-task-runner` records no repos, yet it writes code. So:

- A run's **first wake gets everything**, because it doesn't yet know what it'll need.
- Later wakes get core plus modules chosen from what the run has actually used.
- A checking wake always gets `checking-done`.
- **Any wake can load a module on demand:** `otto state guide <topic>` *(proposed)*. The core lists
  every topic in a line each, and a refusal from `otto state` names the topic to read.

**Items:**

- **3.1 Split with no change in behaviour (M).** Compile modules in, and compose them so the result
  equals today's text. A test asserts it. Add `harness/` to `documents()` in `src/doc_examples.rs`.
- **3.2 `otto state guide` (S),** with the index in the core.
- **3.3 Selection behind a policy (M).** `policy.harness`: `all` or `auto`, absent means `all`. Replace
  `the_harness_is_byte_identical_across_runs` (`src/wake/prompt.rs:157`) with a test that one
  composition is stable.
- **3.4 Fix the harness hash (S).** `src/feedback.rs:224` hashes the harness to spot reports from an
  older version. With per-run text, every run would look older, so hash the whole module set instead.
- **3.5 Map live tests to modules (S),** so `test/live.sh` can run what a change touched. The full set
  still runs before a release.

**Migration:** existing runs stay on `all` until moved one at a time ([table](#run-by-run)). If a run
loads the same module on demand repeatedly, add it to the run's set.

**Measure:** cold-start cache creation before and after, and feedback reports per wake. If reports
about missing instructions rise, widen the selection.

## Phase 4: kernel and apps

**The problem.** The README says otto "contributes none of the doing", yet its largest file is
`src/changes.rs` at 3,717 lines, and 14 other files reference it. The kernel can't be tested or changed
without the landing system, and every app addition touches `core.rs`, `human.rs`, `event.rs` and
`state/commands.rs`.

**Design.** Three layers, with dependencies pointing one way only:

| Layer | Modules |
|---|---|
| **Kernel** | `state`, `event`, `clock`, `paths`, `exec`, `error`, `liveness`, `spawner`, `detach`, `wake`, `poke`, `progress`, `gate`, `notes`, `todo`, `config` (core) |
| **Apps** | `changes` with `state/change` and `agents`; `outputs`; `messages` with `inbox`; `feedback`; `chat` |
| **Surfaces** | `core`, `human`, `cli`, `server`, `story`, `web/` |

An app gives the kernel a small interface: its harness modules, what it adds to a progress mark, what
must finish before a done claim holds, what it notifies about, and anything to do when a wake completes.

**What must not change:** the on-disk layout, journal format, CLI commands and flags, web API, and
`otto state` commands. Skills and check scripts call these, so this phase ships with no migration at all.

**Items:**

- **4.1 App interface (M)** on the kernel, with `feedback` moved first as the smallest app.
- **4.2 Split `event.rs` (M).** Each app owns its events, and the journal bytes stay the same. Confirm
  first that nothing deserializes the journal into `Event`; a search found no such reader.
- **4.3 `outputs` and `messages` (M each).**
- **4.4 `changes` and system agents (L),** in several changes. Split `state/commands.rs`, `core.rs` and
  `human.rs` along the same lines as each app moves.
- **4.5 Separate crates (M).** A Cargo workspace with `otto-kernel` as its own crate. This goes last,
  and it's the point of the phase: the compiler then refuses a kernel-to-app dependency, instead of
  relying on review. The binary and install path stay the same.

**Tests:** before and after each item, the [rehearsal](#rehearsal) output must be identical. Add a
kernel test suite that runs with no apps loaded.

**Stopping early is fine.** If 4.1–4.3 show the interface is wrong, or 4.4 isn't paying off, leave
`changes` in place and say so here. Three clean apps beat a forced fourth.

## Phase 5: execution seam

**You don't need a new host:** the machine is an always-on desktop. So this is a boundary around things
otto doesn't control, not a port.

**Items:**

- **5.1 Platform interface (S).** Put `launchctl`, `osascript` and `caffeinate` (`src/launchd.rs`,
  `src/notify.rs`, `src/wake/launcher.rs`) behind one interface, with macOS as the only real
  implementation. No Linux port.
- **5.2 Model runner interface (S).** Argv building and usage reading (`src/wake/transcript.rs`) behind
  one interface. The harness should reach it through a function, not a constant.
- **5.3 Contract test for `claude` (M).** otto depends on behaviour no document promises: `claude
  '<prompt>'` with stdin at `/dev/null` exits by itself, a variadic flag swallows a trailing prompt, and
  transcripts have a particular path and format. A live test checks each, and it runs whenever the
  installed `claude` version changes, so an upgrade fails loudly instead of quietly producing wakes with
  no prompt or unknown usage.

**Migration:** none.

**Separate decision:** after a restart, poke doesn't run until someone logs in. See [D4](#decisions-for-you).

## Migrating existing runs

Sixteen runs exist. All are on `schemaVersion` 2, and as of today no gate is open, the inbox is empty and
no change is waiting. **Check this again before each cut-over, since runs keep working.**

### Strategy: no schema bump

`read_run` refuses any version but its own (`src/state/mod.rs:1009`), and a run it can't read gets
skipped by poke until a person looks. So bumping `schemaVersion` would strand every run if it went
wrong, and an older binary could never read a migrated run again, which would break rollback.

**Nothing in this plan needs a bump.** Every change is an additive optional field, a new file outside
the run, or a launcher name. That's how the format has grown so far. If something later truly needs a
bump, it gets its own migration command, tested on a copy, and rollback is rethought first.

### What must survive

Compared before and after every cut-over, by a script *(proposed: `scripts/migration-check.sh`)*:

- **Identity:** id, name, number, former id, and every alias, including `once` for `gtd-task-runner`.
- **Purpose:** `goal` and `doneCondition`, byte for byte, by hash. A goal is never rewritten.
- **Schedule:** `nextWakeAt`, `periodMinutes`, `periodAt` (the weekly 07:00 runs), and pause state,
  including the babysitter's "not started".
- **Conversation:** open gates, pending and standing notes, unread messages, drafts.
- **Work:** every output version, every change record and patch, `artifacts/`, journal, handoff.
- **Journals are append-only:** the old journal must be an exact prefix of the new one.
- **Checks:** each script's hash, and its `noChangeTotal` and `wakeAfter`.
- **Worktrees:** the `git worktree list` of each repo in play.
- **`feedback.jsonl`** and `config.json`, apart from the launchers the plan adds.

**Notes in flight:** a one-off note given to a wake but not yet delivered stays pending, and an older
note with no `from` still renders correctly.

**Changes in flight:** a change already approved but not landed when 1.4 ships has no record under
`approvals/`. It goes back to waiting on you, with a message saying why, rather than being trusted or
having a record invented for it. The 17 finished changes are history and aren't checked.

### Rehearsal

Every release touching state rehearses on a copy first:

1. Copy `~/.otto` (26MB) to a temporary `OTTO_HOME`.
2. Run the new binary with `otto ls`, `otto state list --json`, `otto changes --all --json`, and
   `otto poke --dry-run --verbose`. Dry-run spawns nothing.
3. Diff against the installed binary's output on the same copy. Anything unexplained stops the release.
4. Run the migration-check script.

`install.sh` already checks that a new build can read your runs (`target/release/otto ls`). This becomes
part of that check.

### Rollback

`./install.sh --rollback` restores the binary and nothing else. **Two things can defeat it today:**

- **`config.json` is strict.** `Config` and `LauncherDef` use `deny_unknown_fields`
  (`src/config.rs:30`, `:58`), so any new key makes an older binary refuse the whole config.
  **So:** add no new config keys in Phase 1 (profiles use the existing launcher fields), and have
  `install.sh` snapshot `config.json` beside `otto.previous`, restoring both together.
- **Older binaries drop fields they don't know** when they rewrite `run.json`. Item 2.1 fixes that from
  then on. Until it ships, no field is added, and nothing in Phase 1 needs one.

**Before each cut-over,** take a snapshot: `tar` `~/.otto` to `~/.otto-snapshots/<date>-<phase>.tar.gz`.
This is for corruption only, since restoring one discards everything runs did since.

### The waves

Enforcement moves one run at a time, on the same mechanism at each step:

1. **Observe.** Switch the run to a report-only profile (spike question 2). Nothing is blocked; denials
   are logged. If the spike finds report mode doesn't work, observe by running enforced with the run's
   ordinary work checked by hand, wave by wave.
2. **Review.** Each denial is either added to the run's profile or left as a denial. You decide, from
   the report.
3. **Enforce,** when the run has done at least one real stretch of work with no unexplained denial, and
   for hourly runs, 7 days have passed.
4. **Watch** for three real wakes, using the journal and `otto feedback`.
5. **To undo:** switch the launcher back. It's one field, and it takes effect on the next wake.

The order goes from least to most dangerous if it breaks:

| Wave | Runs | Why here |
|---|---|---|
| **A** | `legenda-curate`, `big-idea`, `architect` | No code changes reach a repo. They read the web, so they gain the most. Weekly runs take longer to observe; trigger a wake by hand if waiting is too slow |

## Decisions for you

| # | Decision | My recommendation |
|---|---|---|
| D1 | Seatbelt or a separate macOS user, if the spike shows the Keychain won't split | Decide after 1.1. If it won't split, separate user |
| D2 | `otto-build` installs with `./install.sh`, which replaces the binary poke runs unsandboxed. Granting it that makes the sandbox pointless | Move installing outside the model: after a landing on the otto repo, the same non-model step that pushes runs `./install.sh`. The goal says "If a change is landed, run ./install.sh", so tell it through a standing note that this is now done for it, and have it verify |
| D3 | Do pull-request repositories matter soon? They keep a credentialed lander until `gh` gets the 1.5 treatment | No: both repos are `direct`. Build it when a repo needs it |
| D4 | After a restart, poke waits for login. Auto-login fixes that, but it's a security tradeoff on a machine holding credentials | Leave it off, and have otto notify on the first poke after a long gap, so you can see what was missed |
| D5 | Who builds this? `otto-build` could, but Phase 1 builds its own cage | `otto-build` for 0 and 2–5, each as a change. Phase 1's profiles and enforcement get your direct review |

## Risks

| Risk | Effect | Response |
|---|---|---|
| Keychain can't separate `claude` from `gh` | Seatbelt design fails | Separate user (D1). Found in the first item, before anything depends on it |
| `sandbox-exec` is removed from macOS | Profiles stop working | The launcher mechanism means a replacement is a config change. Contract test catches it |
| A too-tight profile silently degrades a run | Wakes "succeed" with less work done | Observation first; watch three wakes; denials are logged |
| Harness selection hides something a wake needed | Wakes improvise or fail | On-demand loading, first wake gets everything, per-run rollback to `all` |
| Kernel split stalls partway | Half-moved code | Each item lands alone, and stopping after 4.3 is allowed |
| Self-editing `otto-build` breaks itself | The builder is stuck | Existing rollback, plus rule 6: it can't change its own enforcement |
